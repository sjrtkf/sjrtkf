# 정시 API 진입 · v0.9.28

## 현재 동작

**예약 시각 API 진입은 버튼 활성화를 기다리지 않는다.** 사용자가 선택한 경기의 공식 경기·장소·판매 시작 시각을 확인하고, 정상 스포츠 예매의 SSO → partner → 준비 화면 경로를 미리 연다. 준비 화면에 도착하면 서버 시각과 보정값으로 예약을 연결한다.

서버 시각은 공식 getServerTime의 밀리초 응답으로 보정한다. 최근 유효 표본만 예약에 사용하며 단조 시계를 기준으로 계산한다. 일반 HTTP Date는 표시용이고 예약 실행에는 쓰지 않는다. 보정값은 −250~+250ms이며, 음수는 공지 시각보다 앞당긴다. 진입 방식과 보정값은 settings.json에 자동 저장하고 시각 표본은 저장하지 않는다.

예약 시각에는 현재 준비 화면의 원래 enterTicketWaitingPage 콜백을 한 번 실행한다. 화면 버튼을 감싸는 disabled 조건은 예약 실행 조건에서 제외하지만, 원래 콜백 내부의 로그인·차단·진행 중 검사와 서명 생성은 유지한다. 인증 값이나 서명을 복제해 별도 요청을 만들지 않는다. 실제 요청은 사이트 함수가 수행하는 POST secure-url이다.

사이트 자체 자동 진입이 먼저 시작해도 같은 요청 전송 제한을 적용한다. 보정된 기한 전에는 전송하지 않고, 전송한 요청이 있다면 추가 요청을 보내지 않는다. 요청 없이 끝난 예약 콜백, 미개방 응답, 인증 실패, 불명확한 결과는 중지한다. 활성화 감지 방식으로 자동 전환하지 않는다.

현재 React 트리에 연결된 원래 콜백의 공개 코드 계약을 확인한 경우만 실행한다. 준비 화면 배포 코드가 바뀌면 지원 계약을 다시 확인해야 하며, 비슷한 함수를 추정하여 호출하지 않는다. 오래된 트리의 콜백도 사용하지 않는다.

이미 열린 좌석 화면에서 시작하면 새 진입 API나 예약을 만들지 않고 해당 화면부터 진행한다. 일반 좌석 후보와 각 등급의 첫 적격 일반 가격을 확인한 뒤 선점·가격 검증·결제 또는 주문 화면 도착까지 처리한다. 결제를 제출하지 않는다.

## 로그와 제한

- entry-preparation: 정시 진입을 위한 사전 화면 이동.
- entry-trigger: 콜백·타이머·요청 지연. requestDeadlineDelayMs는 예약 기한 대비 클라이언트의 실제 요청 전송 지연이다.
- entry-request / entry-response / queue-response: 요청·응답·대기열 관측을 구분한다. secure-url 성공만으로 대기열 접수나 순번 확보를 단정하지 않는다.
- 보안문자·쿠키·서명·인증값·원문 응답은 로그에 남기지 않는다.

서버 시각에는 통신에 따른 추정 오차가 있으며 브라우저 지연·PC 절전·탭 폐기·사이트 변경으로 실행이 늦거나 중단될 수 있다. 정확한 밀리초 접수나 순번 개선을 보장하지 않는다. 오픈 이전 요청이 거절돼도 자동 반복하지 않는다.

## 검증 범위

격리 Chromium에서 비활성 버튼 상태의 정시 요청, 기한 전 전송 차단, 중복·지연·중지·시각 만료와 좌석→일반 가격→다음 화면을 확인한다. 화면 저장·재실행도 별도 검사한다. 최종 개수와 통과 여부는 배포본 검증결과.json을 기준으로 한다.

실제 사용자 세션 검증은 앱의 기존 Chrome 연결과 실제 자동 진행 명령을 사용하며, 읽기 전용 점검과 좌석 1매 검증을 구분한다. 실제 경기·회차를 확인하고 일반 좌석만 사용하며 결제 화면에서 멈춘다. 연결 실패나 실제 잔여 일반 좌석 부족은 실제 검증 완료로 기록하지 않는다. 로컬 응답으로 진행한 테스트를 실사이트 성공으로 표시하지 않는다.

2026-10-20 사용자는 현재 일반 좌석이 남은 경기가 없다고 확인했다. 따라서 이번 배포의 실제 일반 좌석 선점 → 일반 가격 → 결제 화면 검증은 미완료다. 브라우저 조작 도구는 초기화 오류가 발생했지만, 배포본의 읽기 점검으로 실제 Chrome 연결과 수원FC 경기 목록은 확인했다. 일반 좌석이 있는 실제 예매 화면에서 남은 검증을 수행해야 한다.
