# 예매 진입 조사와 권장 운영 방식

## v0.9.21 반영 결과 · 2026-10-19

**경기 목록의 비활성 버튼을 기다리는 기능을 실제 시작 경로에 연결했다.** `src/chrome-main.js`에서 선택 경기와 공식 공개 API의 경기 정보를 대조한 뒤 `src/entry.js`의 `armListing`을 설치한다. 선택한 카드의 현재 버튼이 `disabled`가 아니고 `aria-disabled`가 `true`가 아니며 문구가 `예매하기`일 때 사이트 함수를 한 번 실행한다. 버튼 요소가 교체되어도 현재 요소를 다시 확인하며, 다른 경기의 활성화로 진입하지 않는다.

기본 활성화 감지는 서버 시각 조회 없이 동작한다. 예약 모드에서는 유효한 서버 시각 설정과 버튼 활성화가 모두 필요하다. 예약 시각이 지났어도 비활성 버튼을 강제로 열지 않고, 목록 감시의 시각 설정이 만료되면 재교정 전까지 진입하지 않는다. 정상 전환으로 새 문서에 도착하면 예약 조건을 그 문서에 다시 연결한다.

목록 → 준비 화면·대기열·좌석 화면의 정상 전환을 이어간다. 새 팝업으로 대상을 전환할 때 부모 목록의 감시 중지 응답을 확인한 뒤 새 게이트를 진행한다. 중첩 팝업이나 새 팝업의 일시적 누락에서도 이 확인 절차를 유지한다. 같은 화면의 재로드, 선택 대상 유실·중복, 사이트 함수 오류에서는 중지하며 동일 실행의 감시를 다시 설치하지 않는다. 화면 이동 중 동작 명령의 응답이 사라져도 동작을 재전송하지 않고 실제 이동 경로를 확인한다. 중지는 감시의 새 호출을 막지만 이미 호출한 사이트 함수의 자체 비동기 작업까지 취소하는 기능은 아니다.

시작 위치 `startPage`와 `listing-trigger`·`entry-request`·`queue-response` 기록을 연결하여 목록 감지 → 함수 실행 → 요청 → 대기열 응답의 지연을 구분한다. 빠른 문서 이동 등으로 관측하지 못한 값은 0ms로 채우지 않는다. 이 기록은 클라이언트 관측 시각이며 서버 내부 접수 시각이나 확보한 순번의 증거를 대신하지 않는다. 진입 HTTP, 대기열 응답 분류, 좌석 처리의 기존 v0.9.20 정책은 유지한다.

앱과 Chrome 확장은 모두 v0.9.21을 사용해야 한다. 새 앱에서 **확장 업데이트 적용 · 다시 연결**을 실행하고 예매 탭을 새로고침한다. 구현과 로컬 검증은 완료했으며, 최종 단위·패키지 검증 결과는 배포본의 `검증결과.json`을 참고한다. 실사이트 자동 활성화 전환, 목록과 준비 화면의 실제 속도 비교, 서버 접수·순번 개선 효과는 아직 확인하지 않았다.

## v0.9.20 반영 결과 · 이전 버전 기록

기본 활성화 감지와 페이지 내부 실행은 유지하고, ±1초·30ms 서명 요청 재전송은 제거했다. 예약 모드는 보정 시각과 사이트 활성화를 함께 요구한다. 준비 화면의 사이트 함수가 요청 없이 끝난 경우에만 1초 후 재확인하며 함수 실행은 최대 3회다. 실제 요청이 발생한 경우에는 중복 전송하지 않는다. 명시적 미개방 코드라도 진입 API 재시도 계약이 확인되지 않은 `P40057`은 자동 재전송하지 않는다. 이 준비 화면 정책은 v0.9.21의 목록 함수 1회 실행과 구별한다.

기존 CDP 네트워크 관찰 기능에 연결 단계 계측과 대기열 `line-up`·`rank` 응답 분류를 추가했다. `/waiting` URL만으로 접수 완료를 표시하지 않는다. 서버가 공개하지 않은 값은 추정하여 채우지 않는다. 사전 연결과 Worker는 효과가 측정되지 않아 추가하지 않았으며, 중지·연결 확인 통신은 유지한다.

실제 접수 확인은 해당 응답을 관측하고 읽은 경우에 한한다. 기록 시각은 클라이언트의 관측 시각이며 서버 내부 접수 시각이 아니다. 응답 본문·대기열 식별자는 저장하지 않는다.

## 예매 전 페이지의 자동 활성화 — 사용자 관찰

2026년 10월 18일 사용자가 예매 전 경기 목록 페이지에서도 새로고침 없이 예매 버튼이 자동 활성화되는 것을 확인했다고 알렸다. 이 관찰에 따르면 해당 화면에서는 카운트다운 페이지에 미리 들어가서 기다리는 것이 필수는 아니다. 모든 상품·화면에서 동일하게 동작하는지는 아직 검증하지 않았다.

v0.9.20의 실제 시작 경로는 목록에서 `prepareEntry`를 실행하여 준비 화면으로 먼저 이동했다. 이 함수는 선택한 경기 버튼이 비활성이면 오류로 중지했고, 당시 `armEntry`의 목록 감시 코드는 시작 경로에 연결되어 있지 않았다. v0.9.21은 새 `armListing`을 실제 시작 경로에 연결하여 이 구현 누락을 보완했다.

현재 지원하는 흐름은 **선택한 경기의 목록 화면에서 대기 → 정상 버튼 활성화 감지 → 사이트 진입 함수 1회 실행 → 정상 이동·대기열 접수 관찰**이다. 중간에 준비·카운트다운 화면이 나타나면 기존 흐름으로 이어간다. 접수 완료 표시는 해당 대기열 응답을 관측하고 읽은 경우에 한한다.

2026년 10월 19일 읽기 전용 조사에서는 공개 목록의 경기·버튼 텍스트를 확인했다. 브라우저 실행 환경 문제로 현재 DOM의 `disabled` 전환이나 실제 진입 함수·이후 경로를 직접 측정하지 못했다. 따라서 기존 DOM 계약과 공식 경기 정보 대조에 기반한 구현 및 격리 테스트의 결과를, 오늘 실사이트의 자동 활성화 동작을 검증한 결과로 확대하지 않는다.

목록 대기가 카운트다운 화면 대기보다 빠른지는 미확인이다. 목록에서 진입할 때 준비 화면이나 인증 단계를 추가로 거칠 수 있으므로, 두 경로의 활성화 감지부터 실제 접수 확인까지 시간을 비교해야 한다. 이를 순번 우위가 확인된 방법으로 안내하지 않는다.

## 후속 보완 과제

- [x] **예매 전 목록 페이지의 활성화 대기 지원 — 구현·로컬 검증 완료.** 선택한 경기의 비활성 버튼을 기다리도록 실제 시작 경로에 연결했다. 경기 일치, 중지·재시작, 버튼 교체, 다른 경기, 비동기 오류, 중복 실행 방지와 준비 화면 전환을 격리 환경에서 검증했다.
- [x] **첫 진입 지연을 구분하는 기록 — 구현 완료.** 시작 위치, 목록 활성화·함수 호출, 진입 요청, 대기열 응답을 구분해 기록한다. 기록되지 않은 값과 서버 내부 시각은 추정하지 않는다.
- [ ] 현재 실사이트에서 자동 활성화 속성·문구 전환과 실제 정상 진입 경로를 관찰한다. 사용자 관찰과 기존 코드 조사만으로 모든 경기의 동작을 일반화하지 않는다.
- [ ] 목록 대기와 카운트다운 화면 대기의 실제 진입 경로 및 지연을 비교하여 기본 대기 위치를 결정한다. 자동 활성화가 확인되지 않은 화면까지 같은 동작을 가정하지 않는다.

- [ ] **첫 요청 지연에 따른 순번 손해 가능성 줄이기 — 미완료.** 중복 진입을 막아도 첫 요청 자체가 늦게 전송되거나 서버에 늦게 접수되면 순번에서 손해를 볼 수 있다. 현재 방식이 가장 빠른 접수나 유리한 순번을 보장하지는 않는다.
- [ ] 정상 이용 중 활성화 감지 → 함수 실행 → 요청 시작 → 응답 → 대기열 접수 확인의 시간을 모아 지연 구간을 구분한다. 전면·최소화 상태와 혼잡 상황의 차이도 확인한다. 클라이언트의 응답 관측 시각으로 서버 내부 접수 시각이나 손해 본 순번 수를 단정하지 않는다.
- [ ] 측정으로 확인된 지연부터 줄이고 같은 조건에서 변경 전후를 비교한다. 요청 중복 방지와 중지 후 이동 방지가 유지되는지 함께 검증한다. 순번 개선 효과는 별도로 확인하며, 응답이 늦다는 이유만으로 병렬 요청이나 반복 전송을 추가하지 않는다.

## 변경 전 조사와 판단 근거

2026년 10월 18일 기준. 권장 방식은 공식 개방 상태에서 한 번 진입하고, 응답이 불확실하면 기존 진행 상태를 확인하는 것이다. 서버 시각 보정과 사전 준비로 첫 요청의 지연을 줄이되, 30ms 반복 호출을 유리한 기본값으로 삼을 근거는 없다. 아래 권장 사항은 설계 제안이며 v0.9.19에 모두 구현된 상태가 아니다.

## 권장 실행 순서

1. 미리 로그인·인증·경기와 회차 확인을 끝내고 예매준비 화면을 유지한다. 확장 업데이트와 연결 확인도 오픈 직전에 하지 않는다.
2. 공식 오픈 시각과 서버 시계의 차이를 표시하되 측정 왕복 지연을 함께 표시한다. 왕복 시간의 절반은 편도 지연의 추정치일 뿐이며 서버 처리·상하행 비대칭 때문에 정확한 오차가 보장되지 않는다.
3. 자동 활성화 화면에서는 사이트의 정상 개방 상태에 즉시 반응하여 진입을 한 번 실행한다. 새로고침이 필요한 화면은 별도 흐름으로 다룬다. 예매 진입 요청 자체로 개방 여부를 고빈도로 탐색하지 않는다.
4. 진입 요청은 동시에 한 개만 유지한다. 명시적인 미개방 거절을 받았을 때만 정상 흐름의 재시도 조건을 확인한다. 클라이언트에서 관찰한 처리 후 1초 대기는 보수적 기준으로 삼을 수 있지만, 서버가 허용을 보장하는 간격은 아니다.
5. 이동 주소 발급, 대기열 접수, 순번 확인, 예매 화면 도착을 별도 상태로 기록한다. 대기열 접수가 확인되면 새 진입 요청을 중단하고 사이트가 정한 대기 흐름을 유지한다.
6. 타임아웃·연결 끊김은 결과 불확정으로 취급한다. 기존 페이지·대기열 상태를 확인하기 전 재전송하지 않는다. 차단·인증 만료는 자동 진입을 중지한다. 서버가 재시도 시점을 제공하면 그 시점을 따른다.

## 응답 지연과 순번

요청 전송 후 400ms 뒤 응답을 받았다는 사실만으로 순번도 400ms 뒤에 부여되었다고 볼 수 없다. 접수가 서버에서 먼저 끝났을 수 있고, 반대로 이동 주소 발급 뒤 별도 대기열 접수가 필요할 수 있다. 이 사이트의 `secure-url` 응답은 이동 주소 발급이며 그 자체로 순번 확보의 증거가 아니다.

미개방 거절을 400ms 뒤에 받는 경우 다음 시도가 늦어지는 손해는 실제로 가능하다. 그러나 중복 요청의 서버 처리 규칙이 확인되지 않은 상태에서 병렬 재전송으로 이 손해를 안전하게 제거할 수 있다고 보장할 수는 없다. 첫 성공 응답만 사용하는 처리는 브라우저 내부 결과 선택일 뿐, 이미 서버로 보낸 다른 요청의 효과를 취소하지 않는다.

따라서 현재의 선택은 최상위 순번을 보장하는 방법이 아니라, 불필요한 로컬 지연을 줄이면서 차단과 중복 진입으로 인한 손실을 줄이는 방법이다. 실제 개선 평가는 첫 요청 시점, 응답 완료, 대기열 접수 확인, 순번 최초 표시를 구분한 측정으로 해야 한다. 서명·쿠키·대기열 키·원문 응답은 로그에 남기지 않는다.

## v0.9.19 당시 동작과 남은 작업 · 이전 기록

- 현재 예약 모드는 ±1초 구간에서 최소 30ms 간격, 동시 요청 1개를 사용한다. 이는 구현된 실험 설정이며 권장 기본값으로 검증된 설정이 아니다. 이번 문서 업데이트는 동작을 바꾸지 않는다.
- 재시도 대상으로 둔 `P40057`은 공개 예매 화면의 미개방 코드다. 진입 API `secure-url`에서 실제 반환되는지는 확인되지 않았다. 확인 전에는 진입 API의 확정된 재시도 계약으로 취급하지 않는다.
- 이동 주소 검증은 있지만 `src/chrome-main.js`는 `/waiting` URL만으로 대기열 진입 상태 문구를 표시한다. 실제 접수·순번·중복 세션·만료 상태를 확인하는 작업이 남아 있다.
- 서버 시각 오차 범위 표시, 재시도 정책 변경, 단계별 접수 확인을 먼저 개선하고 실제 정상 사용 중 수집한 제한된 메타데이터로 병목을 평가한다.
- 로컬 단위 테스트와 격리 Chromium 테스트는 실서비스의 혼잡 시간 지연이나 성공률을 증명하지 않는다.

## v0.9.19 당시 GitHub 반영 전 검증

당시 v0.9.19 소스에서 단위 테스트 전체, 확장 빌드, 격리 Chromium의 진입 HTTP 테스트와 클릭 없는 전체 흐름 테스트를 통과했다. 전체 흐름 테스트는 최소화된 창에서 DOM 입력 이벤트 0회, 로컬 응답 12회로 결제 화면 경로까지 확인한다. 실제 예매 서버 요청이나 결제 제출을 수행한 결과가 아니다. 현재 v0.9.21의 최종 검증 결과는 배포본의 `검증결과.json`을 참고한다.
